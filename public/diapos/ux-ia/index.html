    Quatre qualités à viser. Deux moyens pour y arriver : le design system et l’analyse comportementale.

    Bloc 1, design system : la cohérence rendue réutilisable

    Un design system rassemble règles, composants et modèles réutilisables. Les variables (couleurs, polices, rayons, espacements) en sont les fondations.

    Même rôle, présentation et comportement cohérents. Une différence doit avoir une raison compréhensible.

    Bloc 2, friction : organiser les choix pour décider

    Bloc 2, friction : petit et loin, difficile à atteindre

    Atteindre : loi de FittsUne cible grande et facile à atteindre réduit l’effort. Sur mobile, à vérifier avec les personnes concernées.

    Un principe pour guider les choix, pas une règle pour tout agrandir : le rôle, la position et le contexte comptent.

    Bloc 4, analyse comportementale : observer ce que font vraiment les utilisateurs

    Hotjar : cartes de chaleur, enregistrements de sessions, clics. Clarity, gratuit, existe aussi.

    • Disponible une fois le site en ligne.
    • SaaS et application : des outils d’analyse de produit mesurent l’activation et la rétention.
    • Elle aide à repérer où approfondir. Les comportements observés ne prouvent pas leur cause.
    • Suisse (LPD + LTC) : informer et permettre l’opposition au suivi ; consentement préalable selon les traitements.

    • Vraie attente : on la réduit d’abord. Spinner ou skeleton : un retour adapté aide à comprendre ce qui se passe.

    Bloc 6, performance réelle : charger moins, réutiliser mieux

    Ressources

    Alléger les images, le JavaScript et les polices.

    Charger d’abord ce qui est nécessaire pour voir le contenu et agir.

    Requêtes

    Éviter les appels inutiles, répétés ou qui se bloquent les uns les autres.

    Côté serveur, rechercher aussi les calculs et requêtes de base de données trop lents.

    Cache

    Garder temporairement un fichier ou un résultat pour le réutiliser.

    Dans le navigateur ou côté serveur ; Redis est une option de cache serveur.

    Mesurer avant et après, dans des conditions comparables : poids transféré, délais et requêtes bloquantes.

    Le cache doit être renouvelé quand les données changent. Une réservation ou un prix doit rester à jour.

    À vous : expliquer trois problèmes

    L’obstacle

    Sur quel écran, après quelle action ? Quelle conséquence pour la personne ?

    La preuve

    Une capture, une mesure ou une observation que l’on peut vérifier.

    La priorité

    Pourquoi le traiter ? Quelle amélioration proposez-vous ?

    Le rapport retrouve-t-il ce que vous aviez observé ?

    Les événements fournis sont synthétiques : aucun gain de conversion réel ne peut être déduit.

    Audit et débogage : deux modes distincts

    Pour cet exercice : Audit

    Lire le code, tester le site, produire un rapport et proposer des améliorations. Traverse reste cassé.

    Sur un projet autorisé : Débogage

    Audit d’abord, corrections par l’agent hôte, puis tests et nouvel audit dans les mêmes conditions.

    Une nouvelle mesure sur le même site ne constitue pas un avant/après de correction.

    Aucune version corrigée de Traverse dans cet exercice. Le moteur Labo UX ne réécrit pas lui-même l’application.
